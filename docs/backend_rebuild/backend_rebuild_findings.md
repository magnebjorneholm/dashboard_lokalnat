## 1. Pipeline (overengineering)

*The 5-stage pipeline wraps a computation that is genuinely 3 steps on 148-row DataFrames (~50 ms per run, 7 s only when a real DEA solve executes): (1) capital costs (baseline or KENT recompute), (2) efficiency scores (published table / DEA / StoNED file), (3) revenue-frame assembly. It is also a DAG, not a chain — stage_dea provably ignores its pre_dea input — so the linear 5-stage architecture misstates the dependency structure. Stage 1 is a 1:1 deep-copy repack of BaselineData and stage 4 is a two-row lookup that belongs at the API/result layer; the frozen-dataclass layer carries 42 fields of which at least 9 are never read in production. Orchestration code (core + stages + debug_logger + helpers + mini_run, excluding Excel export and the UI helpers misplaced in pipeline/) is 2,047 LOC; a clean implementation of the same computation is realistically 550–650 LOC (capital_costs ~250, efficiency ~60, revenue_frame ~250), with calculations/ (~2,000 LOC) unchanged. For the API rebuild: precompute the baseline result once globally (it is a pure function of static data), expose run(config) -> {per-company frames}, and make per-company extraction a query, not a stage.*

### 2 of 5 stages are ceremony; pipeline is a linear chain over what is actually a 3-node DAG
**Severity:** high · **Status:** adjusted

**Evidence.** stages/baseline.py:41-50 is a verbatim repack of BaselineData with 9 .copy() calls and zero computation (50 LOC). stages/extraction.py (81 LOC) does two row lookups. stages/dea.py:33 declares `pre_dea: Optional[PreDeaStageOutput] = None` and the body never references it; dea.py:12-16 docstring and mini_run.py:77 ('stage_dea never uses pre_dea') confirm DEA depends only on baseline data. Verified: with baseline config, two runs produce byte-identical dea_results and all_revenue_frames; full run = ~0.05s.

**Why it matters.** AI agents reading core.py:94-153 will infer a 5-step sequential dependency that does not exist, and will keep threading unused parameters (core.py:118-122 passes pre_dea_output into stage_dea) through any new feature. The rebuilt API should not inherit a topology that misdescribes the computation.

**Recommendation.** Rebuild as three pure functions: capital_costs(baseline, capex_config) -> df, efficiency(baseline, eff_config) -> df, revenue_frame(capex_df, eff_df, baseline, frame_config) -> df; delete stage 1 (use BaselineData directly) and stage 4 (see separate finding). One orchestrator of ~30 lines composes them.

**Verifier correction.** Evidence correction: stages/baseline.py:41-51 is a near-verbatim repack of BaselineData with 8 .copy() calls and zero computation (it also drops sdf_non_controllable and renames dea_results->dea_baseline). All other evidence verified as stated, including the re-run determinism/timing check (0.04-0.05s, byte-identical outputs). Recommendation correction: the three pure functions are right, but capital_costs must return the dataframe together with its method metadata (capbase_source/capex_method) — post_dea_capex_helpers.py:39-40,111-112 branch on those fields to pick capex/return sources — or the rebuild must replace that branching with a single normalized capital-cost output; revenue_frame also needs user_reid (or extract the user row at the API serialization boundary, which also replaces stage 4's role for the frontend consumers at export_excel.py:771-788 and frontend/results/m5_efficiency_output.py:102-125).

### Baseline result is recomputed per session although it is a pure function of static data
**Severity:** high · **Status:** adjusted

**Evidence.** frontend/utils/case_actions.py:106-110 runs run_pipeline(baseline_data, get_baseline_config(user_reid)) per session/company; config/case_definition.py:248-267 shows get_baseline_config varies ONLY user_reid — all settings are constants. The 148-row outputs (dea_results, all_revenue_frames, all_eff_reqs, all_incentives) are therefore identical for every user and session (verified equal across runs). Each PipelineResult holds ~1.8 MB of DataFrames incl. full copies of all baseline tables; two results live in session state per user, plus a separate ~15-KPI snapshot mechanism (frontend/utils/result_snapshot.py) invented because results are too heavy to persist.

**Why it matters.** In the API backend this pattern becomes redundant compute and per-session server state. The case-vs-baseline comparison the UI needs everywhere (14 uses of .post_dea.user_revenue_frame) is a diff against a global constant.

**Recommendation.** Precompute the baseline result once at startup/deploy (it changes only when data files change) and serve it as a shared artifact; the case endpoint computes only the case run and returns case + delta. This also removes result_snapshot.py — results become small JSON-serializable frames.

**Verifier correction.** Baseline is a pure function of static data files: get_baseline_config (config/case_definition.py:248-267) varies only user_reid, and all 148-row pipeline outputs (dea_results, all_revenue_frames, all_eff_reqs, all_incentives) are verified byte-identical across users; per-company baseline values are trivial row filters. Yet each session recomputes and stores it (frontend/utils/case_actions.py:106-110). The recomputation itself is cheap (~0.05 s measured) — the real problem is the state design it creates: two ~1.9 MB PipelineResults per session (of which ~1.84 MB is duplicated copies of the input tables embedded in BaselineStageOutput/PreDeaStageOutput), non-serializable results that forced a parallel ~15-KPI Firestore snapshot subsystem (frontend/utils/result_snapshot.py), and 16 non-test call sites coupling the UI to heavyweight in-memory pipeline objects. Recommendation for the rebuild: (1) compute the 148-company baseline frames once at deploy/startup as a shared artifact (invalidated only when data files change); (2) slim the pipeline result to output frames only — stop embedding input tables; (3) the case endpoint computes only the case run and returns case + delta-vs-baseline as small JSON. This eliminates result_snapshot.py, the _baseline_reid session cache, and per-session server state.

### OPEX scaling/override (4.1.1/40.1.1) is implemented twice, in two different stages, on two different tables
**Severity:** high · **Status:** adjusted

**Evidence.** stages/pre_dea.py:78-112 applies opex_scaling/opex_override to df_all_companies; stages/post_dea.py:99-109 applies the same business rules again to sdf_controllable. core.py:148-149 threads pre_dea config into stage_post_dea (`opex_scaling=case_config.pre_dea.opex_scaling`). ### Extraction stage is a per-company view masquerading as a pipeline stage
**Severity:** high → medium · **Status:** adjusted

**Evidence.** stages/extraction.py:44-81 = two `df[df['REId'] == user_reid]` lookups packed into an 11-field dataclass. Production reads only 4 of 11 fields: company_name (pages/4_revenue_frame.py:136, frontend/utils/result_snapshot.py:74), efficiency/potential/is_outlier (frontend/results/m5_efficiency_output.py:102-125, pipeline/export_excel.py:771-788). capex/opex/totex/cu/mw/ns are read only by tests and debug_logger. mini_run.py:87-113 re-implements its own user-row extraction instead of reusing the stage.

**Why it matters.** In the React+API target, 'give me company X's numbers' is a response-serialization concern (a query over the all-companies frames the pipeline already produces), not a compute step. Keeping it as a stage forces every result to be re-run per company and spawns parallel extraction implementations (stage_extraction vs mini_run).

**Recommendation.** Delete the stage. Compute all-148 frames once; implement extraction as a result-layer accessor (e.g. result.for_company(reid) or the API endpoint serializer). Tests assert against the frames directly.

**Verifier correction.** Core claim stands: the extraction stage is a per-company projection, not a compute step — stage_post_dea never consumes it (core.py:142-150), production reads only 4 of its 11 fields, capex/opex/totex serve only tests and the debug logger, and cu/mw/ns are read nowhere at all (fully dead fields). Corrected 'why': the problem is not that results must be re-run per company (PipelineResult already contains all-148 frames in dea.dea_results and post_dea.all_revenue_frames), but that the stage adds a fifth pipeline node and an 11-field contract for what is a serialization concern, teaching future AI agents that per-company extraction is compute, and spawning a second ad-hoc extraction in mini_run.py:88-105 because the stage's signature (requires PreDeaStageOutput, lacks super_eff/eff_req fields) cannot be reused. Corrected recommendation: delete the stage and implement extraction as a result-layer accessor or API serializer over the all-companies frames — but in the rebuild, ALSO fold post_dea's per-company projections (user_revenue_frame, user_eff_req_pct, user_incentive_details, stage_outputs.py:113-128) into that same accessor layer; otherwise the per-company binding of PipelineResult survives the deletion of extraction. Severity: medium — a clean instance of pipeline overengineering worth fixing in the rebuild, but an 81-LOC stage with 4 production read sites is a mechanical cleanup, not a high-impact migration blocker.

### debug_logger is 363 LOC of print-based scaffolding, enabled by default in production
**Severity:** medium · **Status:** confirmed

**Evidence.** pipeline/debug_logger.py: 363 LOC, 51 print() calls, single instantiation site (core.py:86). Production calls run_pipeline without debug= (frontend/utils/case_actions.py:108,120), so every user calculation prints ~2.9 KB of report to stdout (measured). ### Silent except-Exception fallbacks mask failures while the unguarded path actually crashes
**Severity:** medium · **Status:** confirmed

**Evidence.** pre_dea.py:347-349 and 417-418: `except Exception: return _method_baseline_pure(...)` — a failed KENT recomputation silently returns baseline numbers for a user who requested a parameter change. Meanwhile a direct invocation of the PARAMETER_CHANGE + direct-WACC path crashed OUTSIDE those guards: merge_kent_with_baseline raised `TypeError: Invalid value '29725.64...' for dtype 'float32'` at calculations/capex/data_mapping.py:122 (full pipeline run, this venv). post_dea.py:246-249 likewise swallows all incentive errors into `return None, None`.

**Why it matters.** This is defensive ceremony in the wrong places: real errors are converted into plausible-but-wrong results (baseline shown as if it were the user's scenario; incentives silently omitted), which is poison for an API whose consumers can't see stdout — and for AI agents debugging numbers that 'look fine'.

**Recommendation.** In the rebuild, let calculation errors propagate to the API error response (HTTP 422/500 with the cause); reserve fallbacks for explicitly modeled cases (e.g. 'incentive data file absent' -> typed result flag, not bare except). Fix the float32 assignment in merge_kent_with_baseline (cast target columns to float64 before assignment).

## 2. Data management & formats

*The data layer is functionally sound but built as accretion around a Streamlit runtime, not as a data pipeline. There is no raw→staging build step: every cold start re-parses three Excel workbooks with sheet-name guessing, re-derives controllable-cost averages, re-merges curated names, and re-aggregates returns — work that belongs in a one-time build script. Measured cost is modest (~290 ms cold baseline load, of which ~150 ms is xlsx; the 2 s runtime shapefile simplification is the real hotspot), so the case for a parquet staging layer is robustness, not speed: the xlsx/raw-sheet formats force fuzzy header sniffing ('medelvärde', 'normv') and Swedish columns deep into calculations/, which is exactly the kind of ambiguity that derails AI coding agents. All six data_loaders modules import streamlit and rely on @st.cache_data (24 cache decorators repo-wide) — the entire caching story evaporates in the API backend. The precompute-bundle pattern (data/new_benchmarking/ manifest signature guard + drift test) is the best idea in the layer and should be generalized into a single derived-data convention. Target layout: data/raw/ (immutable Ei sources incl. the stray root Normvärdeslista xlsx), data/staging/ (all parquet, English columns, REId key, built by scripts/build_staging.py), data/derived/ (stoned, new_benchmarking, simplified geo — each with a uniform manifest).*

### No raw→staging build step: loader re-derives and reconciles three overlapping sources at every cold start
**Severity:** high · **Status:** adjusted

**Evidence.** data_loaders/baseline_data.py:324-435 — load_baseline_data() at runtime: replaces Excel company names with curated csv (steps 1b, lines 345-357), aggregates per-year returns from capcost_a.parquet (line 390), then 'Replaced OPEXp with SDF-derived controllable_cost_average' (lines 394-416) — meaning Data_modeller.xlsx OPEXp, the SDF 'Påverkbara' sheet average, and controllable_a.parquet are three overlapping sources of the same quantity reconciled on every start. It also calls calculation code during load (line 395 imports calculations.opex.cost_aggregation) and rab_data.py:14 imports TEST_MODE from calculations.capex.data_mapping — upward dependencies from the load layer. No script in scripts/ builds capbase_a.parquet, capcost_a.parquet, controllable_a.parquet or all_adjust_vars.csv; their provenance is undocumented (ARCHITECTURE.md §16 lists files, not origins).

**Why it matters.** For the rebuild, an AI agent cannot tell which source is authoritative for any number, and the baseline 'data' is actually the output of load-time computation. The API backend should serve a fixed baseline dataset, not recompute it per process; undocumented provenance makes regeneration impossible if a source changes.

**Recommendation.** Create scripts/build_staging.py that performs all reconciliation once (name override, OPEXp replacement, return aggregation) and writes a single authoritative baseline dataset to data/staging/*.parquet with a manifest (input hashes, generated_at). Loaders in the API become dumb pd.read_parquet readers. Add a data/README.md documenting provenance of every committed file, including externally-built parquets.

### Swedish-column boundary leaks: raw SDF sheets and 'normvärde' force fuzzy header sniffing inside calculations/
**Severity:** high · **Status:** confirmed

**Evidence.** _load_sdf_data renames only the 'ir' sheet (baseline_data.py:268-281); sdf_controllable is stored raw and calculations/opex/controllable_cost_calculations.py:218-245 sniffs columns by substring: `reid_col = 'REid' if 'REid' in sdf_controllable.columns else 'REId'`, loops looking for 'medelvärde'+'2018-2021' and 'separerat yrkandet'. capbase_a.parquet itself has a Swedish column 'normvärde' (verified via pandas), resolved by fragment matching `_resolve(columns, "normv")` duplicated in 3 modules (calculations/new_benchmarking/environment_capex_adjustment/data.py:23, station_capex_adjustment/data.py:25, capex_environment.py:61). calculations/capex/kent_capbase_prep.py:62-158 renames 'År saknas'/'Halvår' inside calculations/. frontend/modules/base/m1_asset_base.py:235 reads a parquet directly, bypassing data_loaders.

**Recommendation.** In the staging build, emit fixed English schemas (rename 'normvärde'→norm_value, flatten the SDF controllable sheet to named columns) and validate them with explicit schema asserts (e.g. pandera or simple column-set checks). ## 3. Naming & identifiers

*Naming is two-faced in this codebase: the load boundary idea (Swedish file columns renamed to English COL_* constants in data_loaders/) is sound and mostly enforced, but three parallel parameter namespaces (Swedish ui_config keys, English dataclass fields, user-manual PID numbers), 20+ year-suffixed column constants that hard-code the 2024-2027 period, and four company-ID systems create exactly the kind of ambiguity that slows AI agents and will leak into the new JSON API if carried over. The user-manual PID strings already collide internally ("3.6.1" means two different parameters depending on file), and the persisted Firestore case format uses ad-hoc Swedish keys (trunkering_max, outlier_krav, paverkbara_method) that the API rebuild will have to either adopt or migrate. The good news: the Ei-native encodings (cat_encode 1-17, half-year timecodes 229-236, Bilaga-4 variable names nf_norm/cemi4_obs, REId) are genuine regulator conventions worth keeping — they just need one documented home each instead of duplicated formulas and ad-hoc converters. For the rebuild, the single highest-leverage naming decision is: one canonical company key, one canonical parameter namespace (semantic keys, PID as display metadata), and tidy long format (year as a column) instead of year-suffixed names.*

## 4. State, config & API readiness

*The state/config layer has a genuinely portable core — CaseDefinition dataclasses, the config_adapter mapping, compute_config_hash, result_snapshot, and the Firebase custom-claims model are all API-ready in concept — but the ui_config contract they sit on is not. ui_config is an untyped Dict whose declared schema (DEFAULT_UI_CONFIG) has drifted badly from what modules actually write and the adapter actually reads, the None-means-baseline convention is already broken by widget-persistence workarounds, keys are part-Swedish, and the persisted Firestore shape is unversioned with heuristic deserializers. ## 5. Calculations core

*The legacy compute core (capex/, opex/, frontier/, incentive/, efficiency/, revenue_frame_assembly.py — about 3,600 of 5,533 LOC) is genuinely sound: KENT steps 5-8 process the full 496,077-row capbase in 0.51s measured, the math is mostly vectorized, and mass is roughly proportional to domain complexity. ## 8. Security & authorization (gap pass)

*The security model is the weakest dimension of the app and most of it cannot be carried into the React + Python-API rebuild. Authorization is effectively cosmetic today: any anonymous visitor can self-register as a "Regulator" or as any of the 148 companies, and the role/REId they choose is written directly into Firebase custom claims with no approval step — so regulator-level access (and read/write/delete access to any company's saved cases, including uploaded KENT capital-base data) costs an attacker a throwaway email and a few minutes. Every authorization check that does exist (zone routing, role-based company selection, case ownership, the 10-case quota, even email verification) lives only in Streamlit application code; Firestore is accessed exclusively through the admin SDK, which bypasses security rules, and no rules files exist in the repo. **Severity:** low · **Status:** unverified

**Evidence.** _firestore_save (frontend/utils/case_storage.py:208-272) and _local_save (349-399) duplicate ~90% of their logic (kent detection, serialization, limit check, created_at preservation) with real divergences: Firestore stores datetime objects, local stores ISO strings; from_firestore (80-109) vs from_dict (73-77) apply different defaulting. Selection between them is runtime-implicit via _use_firestore() (112-119).

**Why it matters.** Two write formats for the same logical document means the new importer must handle both (users may have local JSON cases from fallback sessions). Divergent code paths with zero tests are where an AI rebuild agent will pick one behavior and silently break the other format.

**Recommendation.** In the characterization suite, run every round-trip test against BOTH backends' serializers (local JSON file and the doc_data dict from _firestore_save with datetimes stringified). In the rebuild, collapse to one storage-agnostic codec with the backend as a thin I/O adapter.
